# 踩坑与决策

这一篇分两部分：**踩过的坑**（含当时的现象与证据，方便下次一眼认出来）和**关键设计决策**（当初为什么这么选，免得后来的人白白推翻一遍）。

# 第一部分：踩过的坑

## 1. 沙箱全部失败，而 DeepTutor 自检说健康

**现象**：`code_execution`、`exec` 两个工具的每一次调用都失败，界面上没有任何异常提示。依赖它们的办公文档技能（生成 docx、xlsx、pptx、pdf）也一直是哑的。

**证据**：

```
backend: BwrapBackend   level: IsolationLevel.SYSTEM
isolation: IsolationLevel.SYSTEM        ← 自检报告「一切正常」

---- python3 -V
  exit=1  out= bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted
---- ls /
  exit=1  out= bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted
```

**根因**：Ubuntu 24.04 默认打开 `kernel.apparmor_restrict_unprivileged_userns = 1`。DeepTutor 用 bubblewrap 时带 `--unshare-all`（含隔离网络命名空间），bwrap 随后要在新命名空间里配置回环网卡，这一步的权限被 AppArmor 拒绝。

**为什么自检查不出来**：`BwrapBackend.health()` 跑一条 `true` 命令，然后**只检查返回结构里的 `error` 字段是否为空**。而 bwrap 进程本身是正常启动、正常退出的，只是退出码为 1、错误信息在标准错误里——`error` 是空的。于是探针判定「bwrap 功能正常」，隔离等级被报告为最高的操作系统级，工具对所有用户开放，但每一次实际调用都失败。

**这个探针缺陷在上游代码里仍然存在。**

**修法**（已做第一条并持久化）：

1. `sysctl kernel.apparmor_restrict_unprivileged_userns=0`，写进 `/etc/sysctl.d/60-apparmor-namespace.conf`。代价是全机放开无特权用户命名空间，安全姿态回退到 Ubuntu 22.04 的水平。
2. 改用 runner 边车容器：设 `DEEPTUTOR_SANDBOX_RUNNER_URL` 指向一个独立容器，沙箱层会自动切后端。上游有现成的 `Dockerfile.runner`。隔离最好。
3. 给 bwrap 配 AppArmor 配置文件。最精细，维护成本最高。

`make verify` 里有一项专门查这个，用的是真跑一条 `echo` 看退出码，不信上游那个探针。

## 2. 产物地址手拼，前端图裂而后端一切正常

**现象**：代码运行成功，图片文件确实写在磁盘上，`is_public_output_path` 也返回真，但浏览器里取回是 404。

**根因**：地址是手拼的 `/api/outputs/workspace/chat/<任务>/code_runs/…`，而 `get_task_workspace("chat", …)` 实际落在 `workspace/chat/chat/<任务>/` 下——中间多一层。

**修法**：地址一律由实际路径相对数据根推导，不手拼：

```python
relative = workdir.resolve().relative_to(path_service.get_public_outputs_root().resolve())
url_prefix = "/api/outputs/" + relative.as_posix()
```

**教训**：凡是「路径 → 对外地址」的换算，都要从同一个真值推导出来。这类错误的表现（图裂）离原因（少一层目录）很远。

## 3. 数据根跟着当前工作目录走

**现象**：同一段代码，在服务里跑好好的，拿到命令行单独跑就把文件写到别处去了。

**根因**：`PathService` 的数据根按 `DEEPTUTOR_HOME` 环境变量解析，没设就按当前工作目录猜。服务是用 `--home ~/DeepTutor-src` 启动的，而我在 `~/DeepTutor-ext` 下跑脚本，于是解析成了 `~/DeepTutor-ext/data/user`。

**修法**：所有独立脚本开头都设一次：

```python
os.environ.setdefault("DEEPTUTOR_HOME", str(Path.home() / "DeepTutor-src"))
```

## 4. 每格新建 WebSocket 连接会撞竞态

**现象**：单格执行没问题，「从头跑到这」连着跑几格时，第二三格必定超时。

**证据**：

```
前置各格（格号,结果）: [(2, 'ok'), (3, 'timeout')]
```

第 3 格的代码在别处实测只要 0.07 秒。

**根因**：新连接刚建立、服务端还没把它接到内核的消息通道上，我们发出去的执行请求已经出去了；内核回消息广播时这条连接还没在收，于是永远等不到「执行完毕」，一直等到超时。

**修法**：每个内核保持一条长连接，连上后先发一次内核信息查询并等回复，确认通道真的通了再开始干活。顺带省掉了每格一次握手。

---

## 5. 可编辑安装改了代码不重启不生效

**现象**：给接口加了一个参数，请求带上它却像没实现一样——返回里那个参数完全没起作用。

**根因**：扩展是 `pip install -e` 装的，改文件不会自动重载已经加载进内存的模块。后端跑的还是旧代码。

**教训**：改完扩展代码就 `make restart`。这一条害我误判过「参数没实现」，白排查了一轮。

## 6. nltk 的工作目录导入拦截误伤

**现象**：建知识库直接失败，错误信息是：

```
Blocked import of regex from current working directory for security reasons.
Use '-P' or set PYTHONSAFEPATH to prevent Python from searching the current working directory.
```

这条信息很误导——看着像是有人往工作目录扔了个假的 `regex` 模块，实际上没有。

**根因**：nltk 新版本装了一个导入拦截器（`nltk/inisec.py`）：凡是 nltk 直接或间接要导入的模块，只要解析出来的路径落在**当前工作目录之内**，就一律拒绝。

而源码部署的形态正好命中：虚拟环境建在项目目录里（`~/DeepTutor-src/.venv`），服务进程的工作目录正是项目根，于是 site-packages 里每一个正经的第三方库都被判成「来自当前工作目录」。

设 `PYTHONSAFEPATH` 没用——那个拦截器看的是路径关系，与 `sys.path` 无关。

**修法**：不把防护整个拆掉，而是给它开一条口子——路径确实在 site-packages 里的模块直接放行，其余仍走原来的判断。实现在 `deeptutor_ext/compat.py`，由站点钩子在 `nltk.inisec` 加载后自动打上。真有人往工作目录扔同名文件，照样拦得住。

`make verify` 里有一项查它。

## 7. 半成品知识库

**现象**：第一次建索引失败（因为上一条），修好后重建，报「knowledge base not initialized」。

**根因**：第一次失败时已经在登记表里留下了名字，但索引没建成。第二次走到「已存在 → 补文档」分支，而底下的索引根本不存在。

**修法**：捕获这个错误，删掉半成品重建，而不是把错误抛给用户。

## 8. 外部课程里必有读不了的文件

**现象**：导入 ML-For-Beginners 整个失败，堆栈指向 `json.loads`。

**根因**：仓库里有两个 `.ipynb` 不是合法 JSON。

**修法**：`parse_notebook` 抛专门的异常，上层跳过并计数，最后如实报告「跳过 N 个文件」。

**教训**：只要允许用户导入任意外部资源，就必须假设里面有坏文件——Git LFS 指针、空文件、坏编码都会出现。**解析失败绝不能让整批失败。**

## 9. 端口在你眼皮底下被占

**现象**：先探测 9184 到 9189 全部空闲，选了 9185，几分钟后启动报端口冲突。

**根因**：9185 是 novnc 的 websockify，在我探测之后才起来。

**教训**：这台机器上跑着不少服务，端口要**在启动脚本里固化并断言**，不要凭一次探测就认定空闲。DeepTutor 自己的行为是对的：检测到冲突就明确报错退出，不默默漂移。

---

## 10. 界面语言决定回答语言

**现象**：明确要求中文回答，模型还是用英文。

**根因**：DeepTutor 的回答语言**跟随网页界面语言**，而界面语言存在每个浏览器自己的本地存储里（`deeptutor-language`），服务端没有全局默认。前端的归一函数写成「取到的值是 zh 才用中文，其余一律英文」，于是任何没手工切过语言的浏览器打开都是英文界面加英文回答。

设置页上写的「只影响界面文案，模型输出语言由你的提示词控制」与实际行为不符——对照实验里用英文提问，中文界面下得到中文回答与中文标题。

**修法**：把那处判断反过来写成「显式选了英文才用英文，其余一律中文」。

- pip 版：改编译好的前端产物（`bin/set-zh-default.py`，`make start` 时自动重放）
- 源码版：改源文件 `web/context/app-shell-storage.ts`，提交在 `local` 分支

---

## 11. 供应商填错会让工具静默失效

**现象**：知识库明明建好了，对话时就是不检索。

**根因**：模型供应商填了 `llama_cpp`（或 `ollama`、`vllm`、`lm_studio`）。DeepTutor 的 `can_use_native_tool_calling` 会因为这些本地供应商标记而**整轮不下发工具声明**，模型自然不会调工具。

**修法**：供应商一律填 `custom`（界面上是「Custom (OpenAI API)」），照样指向本地模型的地址。

# 第二部分：关键设计决策

## 为什么不改 DeepTutor 源码

因为要跟随上游升级。上游发版很快（这次做的过程中就从 1.5.6 到了 1.5.7）。改动越深，每次升级的代价越大，最后的结局通常是不再升级。

代价是接入依赖几个宿主符号，上游改名会静默失效——所以配了 `make verify`。

## 为什么复用 `code` 块类型而不是新增块类型

新增块类型要改后端的枚举（源码改动），而块模型本来就允许自定义字段。复用加自定义字段等于后端零改动，前端只多一个判断，认不得的地方会优雅退化。

## 为什么用自定义事件而不是逐层传回调

书页组件树有三层。逐层加参数会让三个文件都变，升级变基时冲突面更大。事件只需要发端和收端两处。

## 为什么一页一个内核

页在课程里对应一课，也对应一份 notebook。这个粒度最符合学生的直觉：同一课里前后格子共享变量，换一课重新开始。

更细（一格一个）就失去了 notebook 的意义；更粗（一本书一个）会让不同课之间的变量互相污染。

## 为什么产物落在 `code_runs` 目录下

DeepTutor 对哪些路径可以经 `/api/outputs` 公开有一份白名单，`workspace/chat/<任务>/code_runs/` 正在其中。沿用它等于**白蹭一条现成的公开通道**，不用改宿主、不用自己写静态服务。

## 为什么导入答案本而不是练习本

课程给学生的练习本多数只有一个空格子。带讲解和完整代码的是答案本，它才是可以逐格运行的教学材料。

这确实牺牲了「学生自己填空」的教学设计。要保留的话可以两份都导，练习在前、答案折叠在后——目前没做。

## 为什么检索索引是可选的、单独触发的

建索引要把全课正文过一遍向量化，78 篇文档要几分钟。做成导入的必经步骤会让「取一门课」变成一个漫长且容易失败的操作。拆开之后，导入几秒就完成、立刻能读能跑，索引在后台慢慢建。

## 为什么执行容器自建镜像

官方科学计算镜像没有 transformers，而 Hugging Face 的课程从第一章就要用。装 CPU 版 torch 是有意的：这台机器没有显卡，GPU 版会多带一两 GB 用不上的库。

模型缓存放在宿主挂进来的可写目录里，重建容器不用重新下载。

## 为什么内核关在容器里而不是宿主机上

学生在教学场景里本来就要写代码，等于给了任意代码执行能力。实测过：宿主机上跑内核时，一行 `open('…/settings/model_catalog.json').read()` 就能读到模型服务的配置。

容器里同样的代码返回 `False`（看不见），课程原文写入被拒（只读挂载），进程以普通用户身份运行。

## 为什么 opencode 不做成模型供应商

见 [06-opencode 接入](06-opencode接入.md)。简短说：那条路会让 DeepTutor 里所有需要模型主动发起的工具全部失效，而「让 opencode 参与教学」这件事，子代理那条路已经做到了而且做得更好。
