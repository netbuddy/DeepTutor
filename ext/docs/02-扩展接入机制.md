# 扩展接入机制

这一篇讲整套东西的地基：**我们的代码是怎么挂进 DeepTutor 的，为什么这么挂，以及升级时怎么保证还挂得住。**

---

## 问题

DeepTutor 没有给工具留插件入口。源码里有一处看着像入口的钩子：

```python
# deeptutor/runtime/registry/capability_registry.py
def _load_plugin_hooks():
    try:
        module = importlib.import_module("deeptutor.plugins.loader")
    except Exception:
        logger.debug("Plugin loader unavailable; skipping plugin discovery.")
        return None, None
```

但 `deeptutor.plugins` 这个模块**在源码仓库和发行包里都不存在**——它是一个从未实现的预留。而且就算实现了，它只加载能力（capability），代码里明确跳过以 `tool.py` 结尾的清单项，工具进不来。

另一处倒是真的用了标准机制：`deeptutor/partners/channels/registry.py` 通过 `entry_points(group="deeptutor.partners.channels")` 发现外部渠道插件。说明上游懂这套做法，只是没给工具和接口开这个口子。

所以要么改源码，要么自己造一条通路。

---

## 做法：三档改动，各配一种重放机制

按侵入程度分三档。**能放进前一档的就不要放进后一档。**

| 档 | 放什么 | 住在哪 | 升级时怎么办 |
|---|---|---|---|
| 零侵入 | 新工具、新接口、替换服务实现、兼容性补丁 | `deeptutor_ext` 独立包 | 什么都不用做 |
| 配置 | 环境变量、`settings/*.json`、容器编排、Makefile | 源码树之外 | 什么都不用做 |
| 必须改源码 | 前端组件、导航入口、界面文案 | `~/DeepTutor-src` 的 `local` 分支 | `git rebase` |

目前的分布：后端功能**全部**在零侵入档；源码改动只有十个文件、六处嵌入点，全是前端。

---

## 零侵入是怎么做到的

三步。

### 第一步：独立包，装进同一个虚拟环境

```
~/DeepTutor-ext/
├── pyproject.toml          # name = deeptutor-ext
└── deeptutor_ext/
    ├── integrate.py        # 唯一的接入点
    ├── _hook.py            # 导入后钩子的基础设施
    ├── _sitehook.py        # 站点钩子的落点
    ├── compat.py           # 第三方库的兼容处理
    ├── api.py              # 新增的 HTTP 接口
    ├── tools/              # 新增的工具
    ├── kernel/             # 内核会话服务
    └── course/             # 课程模块
```

`pip install -e ~/DeepTutor-ext` 装进 `~/DeepTutor-src/.venv`。

### 第二步：站点钩子，让所有入口都自动加载

Python 启动时会执行 `site-packages` 下 `*.pth` 文件里以 `import` 开头的行。我们放一个：

```
# ~/DeepTutor-src/.venv/lib/python3.12/site-packages/deeptutor_ext.pth
import deeptutor_ext._sitehook
```

由 `bin/install-sitehook.py` 安装，可重复执行。

这么做的好处是**每一个用到这个虚拟环境的进程都会带上扩展**：`deeptutor` 命令、后端的 uvicorn、后台任务进程，全都不必改启动方式。

`_sitehook.py` 必须**极轻**——它只登记回调，绝不在此处导入 DeepTutor 本身，否则每个用这个环境的 Python 进程（包括 pip、各种小脚本）都要付出加载整个 DeepTutor 的代价。

### 第三步：导入后钩子，等宿主模块加载完再动手

这是关键的一环。我们要往 `deeptutor.tools.builtin` 的内置工具清单里追加工具，但那份清单是模块顶层的一个元组，工具注册表在导入时就把它取走了。想追加进去，就得赶在注册表读取之前、在该模块加载完成之后动手。

Python 没有内建这个能力（PEP 369 提出过又撤回了），标准做法是往 `sys.meta_path` 放一个查找器：

```python
# deeptutor_ext/_hook.py（要点）
class _AfterImport(importlib.abc.MetaPathFinder):
    def find_spec(self, fullname, path=None, target=None):
        if fullname != self.module_name:
            return None                      # 别的模块一律放行
        self._detach()                       # 先把自己摘掉，否则下面这次查找会递归
        spec = importlib.util.find_spec(fullname)
        original_exec = spec.loader.exec_module
        def exec_module(module):
            original_exec(module)            # 先让它正常加载
            self.callback(module)            # 再执行我们的回调
        spec.loader.exec_module = exec_module
        return spec
```

`after_import(module_name, callback)` 还处理了「模块已经在 `sys.modules` 里」的情况——那时立即调用回调，调用方不必区分。

回调里出异常一律吞掉并记日志：DeepTutor 少了我们的工具还能正常跑，因为一个异常就起不来是不可接受的。

## 目前登记了三个回调

全在 `deeptutor_ext/integrate.py` 的 `install()` 里：

```python
after_import("deeptutor.tools.builtin", _extend_builtin_tools)
after_import("deeptutor.api.main", _attach_api_routes)
after_import("nltk.inisec", _relax_nltk_guard)
```

### 追加工具

```python
def _extend_builtin_tools(module):
    module.BUILTIN_TOOL_TYPES = tuple(module.BUILTIN_TOOL_TYPES) + (工具类, ...)
    module.BUILTIN_TOOL_NAMES = tuple(t().name for t in module.BUILTIN_TOOL_TYPES)
    module.CONFIGURABLE_BUILTIN_TOOL_NAMES += (可自动挂载的名字, ...)
```

三个名字各有分工：

- `BUILTIN_TOOL_TYPES` — 工具注册表读它来实例化，进了这里工具才存在
- `BUILTIN_TOOL_NAMES` — 从上一个派生，设置页等地方读它
- `CONFIGURABLE_BUILTIN_TOOL_NAMES` — 对话流程读它来决定要不要把工具挂给模型；不进这里，工具只能在 Playground 里手工调用

### 追加接口

```python
def _attach_api_routes(module):
    app = getattr(module, "app", None)
    from deeptutor_ext.api import attach
    attach(app)      # app.include_router(...)
```

时机是安全的：`api/main.py` 顶层执行完（所有官方路由都注册完了）之后、uvicorn 启动之前。

`attach()` 里会先检查路由是否已存在，重复调用不会挂两遍；鉴权依赖尽量复用宿主的 `require_auth`，取不到就挂无依赖版本（单机部署的默认情况）。

## 加一个新工具要做什么

1. 在 `deeptutor_ext/tools/` 写一个类，继承 `deeptutor.core.tool_protocol.BaseTool`，实现 `get_definition()` 与 `execute()`；
2. 在 `integrate.py` 的 `EXTENSION_TOOL_TYPES` 里加上它；
3. 想让对话自动挂载它，再加进 `AUTO_MOUNTED_TOOL_NAMES`；
4. `make restart`，然后 `make verify` 确认它进了注册表。

**不用改前端**：Playground 页面会遍历工具注册表、按工具声明的参数自动渲染表单，还用服务端推送实时回传执行日志。新工具的开发与验收都可以在那里完成。

工具的返回值 `ToolResult` 有几个字段值得知道：`content` 是给模型读的文本，`sources` 会变成对话里的引用卡片，`metadata` 是给前端的结构化提示，`pause_for_user` 能让对话暂停等用户回答。

---

## 加一个新接口要做什么

1. 在 `deeptutor_ext/api.py` 里建一个 `APIRouter`，写好路由；
2. 在 `attach()` 里 `app.include_router(router, prefix="/api/v1/ext/xxx", ...)`；
3. `make restart`。

前端调用时用 `apiUrl("/api/v1/ext/xxx")`——DeepTutor 的前端是「地址无关」的，请求打到前端自己的源，由 `web/proxy.ts` 转发给后端，所以 `apiUrl` 只是原样返回路径。

**注意接口前缀是 `/api/v1/`**，不是 `/api/`。

## 前端改动：只能改源码，所以要集中

前端组件没有插件机制，必须改源码树。策略是**让改动尽量集中、尽量以新增文件为主**。

目前六处嵌入点：

| 文件 | 改了什么 | 行数 |
|---|---|---|
| `blocks/RunnableCell.tsx` | 新增：可运行单元格组件 | 338 |
| `app/(workspace)/course/page.tsx` | 新增：课程管理页 | 约 380 |
| `blocks/CodeBlock.tsx` | 按 payload 里有没有 notebook 信息分派 | 约 25 |
| `blocks/BlockRenderer.tsx` | 把书与页的标识传给 CodeBlock | 4 |
| `book/page.tsx` | 监听单元格发来的提问事件，打开对话面板并预填 | 29 |
| `book/BookChatPanel.tsx` | 多接一个预填参数 | 9 |
| `sidebar/SidebarShell.tsx` | 加一个导航条目 | 8 |
| `locales/{zh,en}/app.json` | 各加两条文案 | 4 |

**为什么用自定义事件而不是逐层传回调**：书页的组件树有三层（页面 → 阅读器 → 块渲染器 → 单元格），逐层加参数会让三个文件都变，冲突面更大。单元格派发一个 `ext:ask-about-cell` 事件，页面那一层监听，中间两层完全不用动。

**词表不要重排序**：`locales/*/app.json` 本来就不是按键排序的，重排会制造大片无谓的差异，升级变基时更难合。只在末尾追加。

### 分支与变基

```bash
cd ~/DeepTutor-src
git checkout -b local           # 本地改动都提交在这
git tag upstream-base v1.5.7    # 记住基于哪个上游版本

# 升级时（make upgrade 会自动做）
git rebase --onto v1.5.8 upstream-base local
git tag -f upstream-base v1.5.8
```

`make patches` 把 `local` 上的提交导出成补丁文件放进 `patches/`。变基之后提交哈希会变，有一份补丁在手更踏实。

`frontend-patches/` 下还留着**生成这些改动的脚本**。上游把某处改得对不上时，改脚本再跑一遍，通常比手工重做省事——脚本里都用了「已经改过就跳过」的判断，可以重复执行。

## 这套机制的代价

**接入依赖三个宿主符号**（`BUILTIN_TOOL_TYPES`、`BUILTIN_TOOL_NAMES`、`CONFIGURABLE_BUILTIN_TOOL_NAMES`）与一个模块级的 `app` 对象。上游要是改了名字，接入会**静默失效**：工具只是不出现，界面上看不出任何异常，等到有人问「怎么用不了」才发现。

`make verify` 就是为这件事准备的，它把这几个符号逐条查一遍。**升级后必须跑，不要跳过。**

另一个代价是**可编辑安装的更新语义**：改了扩展代码不重启后端，跑的还是旧模块。这曾经害我误判过一个功能没实现。改完就 `make restart`。
