# 事件流

上一章的消息是**结果**——一轮结束后才有的东西。但用户不能等：模型吐字要边吐边显示，
工具跑起来要立刻看到「正在执行 read_file」，出错要马上知道。

所以 agent 内部需要一条**事件流**：正在发生的每一件事都作为一个事件发出去，
谁想看谁订阅。

Python 那边用的是「注册回调函数」。Go 这边有更自然的东西：**通道**。

## 事件有哪些

| 事件 | 什么时候发 | 订阅者拿它做什么 |
|---|---|---|
| `text_delta` | 模型每吐出一小段文字 | 追加到界面上，打字机效果 |
| `tool_start` | 开始执行某个工具 | 显示「正在执行 …」 |
| `tool_end` | 工具执行完 | 显示结果或错误 |
| `message_done` | 一条完整消息组装好了 | 存进历史 |
| `turn_done` | 这一轮彻底结束 | 解除输入框的禁用状态 |
| `error` | 出岔子了 | 报错 |

## 本章起点

上一章的类型，这里重新定义一遍——每一章是独立的一页，页与页之间不共享。

```go
// file: blocks.go
package main

import (
	"crypto/rand"
	"encoding/hex"
)

func newID(prefix string) string {
	buf := make([]byte, 6)
	rand.Read(buf)
	return prefix + "_" + hex.EncodeToString(buf)
}

type Block interface{ BlockType() string }

type TextBlock struct{ Text string }

func (TextBlock) BlockType() string { return "text" }

type ToolUseBlock struct {
	ID   string
	Name string
	Args map[string]any
}

func (ToolUseBlock) BlockType() string { return "tool_use" }

type ToolResultBlock struct {
	ToolUseID string
	Content   string
	IsError   bool
}

func (ToolResultBlock) BlockType() string { return "tool_result" }

type Message struct {
	ID      string
	Role    string
	Content []Block
}

func (m Message) Text() string {
	out := ""
	for _, b := range m.Content {
		if t, ok := b.(TextBlock); ok {
			out += t.Text
		}
	}
	return out
}

func NewMessage(role string, blocks ...Block) Message {
	return Message{ID: newID("msg"), Role: role, Content: blocks}
}
```

## 用通道做事件流

Go 里最直接的做法是「一次运行返回一个只读通道，调用方 `range` 它」：

```go
// file: events.go
package main

// Event 事件流上的一个事件。Data 用 map 是为了不让事件类型爆炸——
// 每加一种事件就定义一个结构体，收益不大，反而让 switch 变长。
type Event struct {
	Kind string
	Data map[string]any
}

// EventStream 一次运行的事件流。
//
// 为什么用通道而不是注册回调：
//   - 订阅方用 for range 就能消费，语法上天然是「一个序列」；
//   - 发布方 close 掉通道就表示「结束了」，不需要额外的结束事件；
//   - 消费慢时发布方会阻塞，这是想要的行为——它逼着你去想背压，
//     而回调模型里慢消费者只会悄悄拖慢一切。
type EventStream struct {
	ch chan Event
}

func NewEventStream(buffer int) *EventStream {
	return &EventStream{ch: make(chan Event, buffer)}
}

// Emit 发一个事件。缓冲满时会阻塞，直到消费方跟上。
func (s *EventStream) Emit(kind string, data map[string]any) {
	if data == nil {
		data = map[string]any{}
	}
	s.ch <- Event{Kind: kind, Data: data}
}

// Close 表示不会再有事件了。消费方的 for range 会自然结束。
func (s *EventStream) Close() { close(s.ch) }

// Events 给消费方的只读视图。返回只读通道，消费方就不可能误关它。
func (s *EventStream) Events() <-chan Event { return s.ch }
```

## 边吐边显示

现在让假模型一个字一个字地吐，消费方实时打印。这就是打字机效果的全部原理。

```go
// file: model.go
package main

import (
	"fmt"
	"time"
)

// fakeStreamingModel 假模型：把回答切成小段，一段段发出去，最后组装成一条完整消息。
// 它在自己的 goroutine 里跑，通过通道把事件送出来。
func fakeStreamingModel(prompt string, stream *EventStream) Message {
	answer := []rune("北京现在是下午 2 点 32 分。")
	var collected []rune

	for i := 0; i < len(answer); i += 3 { // 每次吐三个字，模拟真实的分块
		end := i + 3
		if end > len(answer) {
			end = len(answer)
		}
		piece := answer[i:end]
		collected = append(collected, piece...)
		stream.Emit("text_delta", map[string]any{"delta": string(piece)})
		time.Sleep(50 * time.Millisecond) // 放慢一点便于观察
	}

	msg := NewMessage("assistant", TextBlock{Text: string(collected)})
	stream.Emit("message_done", map[string]any{"message_id": msg.ID, "text": msg.Text()})
	return msg
}

var _ = fmt.Sprintf
```

```go
// file: main.go
package main

import "fmt"

func main() {
	stream := NewEventStream(16)

	// 模型在自己的 goroutine 里跑，跑完关掉通道
	var result Message
	go func() {
		defer stream.Close()
		result = fakeStreamingModel("北京现在几点？", stream)
	}()

	// 主 goroutine 消费事件。for range 会一直读到通道被关闭。
	var buffer string
	for ev := range stream.Events() {
		switch ev.Kind {
		case "text_delta":
			buffer += ev.Data["delta"].(string)
			fmt.Printf("\r界面上现在显示：%s", buffer)
		case "message_done":
			fmt.Printf("\n（消息 %s 已完成）\n", ev.Data["message_id"])
		}
	}

	fmt.Println("最终消息：", result.Text())
}
```

跑一下能看到文字是一段段出现的。注意 `for range` 在通道被关闭后自然结束——
**不需要额外的"结束"事件**，这是通道相对回调的一个便利。

## 一条流，多个消费者

上面只有一个消费方。真实场景里界面要看文字增量、日志只关心大事。通道有个特点：
**一个事件只会被一个消费者拿到**，所以不能简单地开两个 goroutine 都去 range。

做法是加一层扇出：一个 goroutine 读源头，转发给多个下游。

```go
// file: fanout.go
package main

// fanOut 把一条事件流复制成多条。
//
// 每个下游一个通道，源头的每个事件都往所有下游发一份。
// 注意这里的代价：任何一个下游消费慢，都会拖慢所有人。
// 真实系统里会给下游加缓冲或丢弃策略，教学版保持最简单的语义。
func fanOut(src <-chan Event, n int, buffer int) []<-chan Event {
	outs := make([]chan Event, n)
	readonly := make([]<-chan Event, n)
	for i := range outs {
		outs[i] = make(chan Event, buffer)
		readonly[i] = outs[i]
	}
	go func() {
		defer func() {
			for _, out := range outs {
				close(out)
			}
		}()
		for ev := range src {
			for _, out := range outs {
				out <- ev
			}
		}
	}()
	return readonly
}
```

改 `main.go` 用它：

```go
// file: main.go
package main

import (
	"fmt"
	"sync"
)

func main() {
	stream := NewEventStream(16)
	go func() {
		defer stream.Close()
		fakeStreamingModel("北京现在几点？", stream)
	}()

	// 一份给界面，一份给日志
	channels := fanOut(stream.Events(), 2, 16)

	var wg sync.WaitGroup
	wg.Add(2)

	go func() { // 界面：逐字追加
		defer wg.Done()
		var buffer string
		for ev := range channels[0] {
			if ev.Kind == "text_delta" {
				buffer += ev.Data["delta"].(string)
				fmt.Printf("\r界面：%s", buffer)
			}
		}
		fmt.Println()
	}()

	go func() { // 日志：只记大事，不关心逐字增量
		defer wg.Done()
		for ev := range channels[1] {
			if ev.Kind != "text_delta" {
				fmt.Printf("[日志] %s\n", ev.Kind)
			}
		}
	}()

	wg.Wait()
	fmt.Println("两个消费者都收到了自己关心的事件。")
}
```

## 为什么不用回调参数

有人会想：直接给模型函数传一个 `onDelta func(string)` 回调不就行了吗？

一开始行，等到事件变多就不行了。工具开始、工具结束、错误、轮次结束……每加一种就要多
一个参数，而且这些参数要从最外层一路传到最里层。事件流把这件事收成一个对象：
**发布方只管发，订阅方只管挑自己关心的**，中间层什么都不用知道。

## 本章小结

- agent 内部需要一条事件流，把「正在发生什么」实时送出去。
- Go 里用**通道**：消费方 `for range`，发布方 `close` 表示结束，不需要额外的结束事件。
- 一个事件只会被一个消费者拿到，**要多个消费者就得扇出**。
- 扇出的代价是**最慢的那个消费者决定整体速度**，真实系统要考虑缓冲或丢弃。
